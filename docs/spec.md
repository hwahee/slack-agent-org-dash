# slack-agent-org-dash 스펙

Slack 에이전트(`slack-agent-org`)가 실행 중에 남기는 진단 기록을 읽어, 사람과 에이전트가 **지금 에이전트의 귀(Socket Mode 수신)가 살아 있는지, 놓친 메시지가 있었는지, 언제 왜 끊겼는지**를 보게 하는 테스트베드입니다. 공통 규약은 [docs/testbed/](testbed/README.md)가 원본이고, 이 문서는 이 테스트베드만의 계약을 정합니다.

## 변경 이력

| 날짜       | 바뀐 절                                                                                                                                                                                                                                    | 영향받는 마일스톤 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------- |
| 2026-11-27 | 10.3 데이터와 표현, 10.4 조작, 10.5 배치는 안 C로 확정, 10.6 기본 배치와의 차이. 13절 3번(M3b 방식)을 2절로: P6를 기다림, 그동안 UI 시험은 실패한 채로 둠                                                                                  | M3a, M3b          |
| 2026-11-27 | 2절 샘플 코어: 스모크 시나리오도 남김(공통 시험이 불러옴, 이 테스트베드에서는 SKIP). 9절·11절 M2: 오류 코드를 실제 공통 런타임에 맞춤(`VALIDATION_ERROR`, `set_config`의 `restart-required` 결과), 고정 데이터 위치 `fixtures/agent-data/` | M1, M2            |
| 2026-11-27 | 최초 작성                                                                                                                                                                                                                                  | M1–M4             |

## 1. 목적

- **검증 대상 제품**: `slack-agent-org` — Slack 멤버 계정으로 일하는 에이전트. 메시지를 Socket Mode(WebSocket)로 받고, 놓친 메시지는 10분마다 도는 따라잡기(Slack 기록 조회)가 건집니다.
- **보고 싶은 실패**: 프로세스는 연결이 살아 있다고 믿는데 실제로는 아무것도 오지 않는 **반쯤 죽은 소켓**. 이때 메시지는 다음 따라잡기까지(최대 10분) 늦게 들어옵니다. 지금까지 확인된 사례는 맥이 잠들었다 깬 뒤와 네트워크가 바뀐 뒤입니다.
- **이 테스트베드 없이 어려운 것**: 제품의 사람용 로그에는 "끊긴 줄 모름"이 남지 않습니다. 진단 파일(`data/diag/`)에는 신호가 있지만, 사람이 터미널로 JSON을 훑어서는 "지금 귀가 살아 있나"와 "놓친 메시지가 있었나"에 바로 답할 수 없고, 제품 레포의 에이전트가 변경(예: 자동 재연결) 뒤에 결과를 판정할 도구도 없습니다.
- 이 테스트베드는 **관찰만** 합니다. 제품에 아무것도 보내지 않고, 제품의 파일을 바꾸지 않고, 제품 코드를 고치지 않습니다.

## 2. 확정된 전제

- 공통 규약([docs/testbed/architecture.md](testbed/architecture.md))의 결정을 모두 따릅니다.
- **레포**: `hwahee/slack-agent-org-dash`(공개). 이름은 사람이 정했고, `testbed-<이름>` 규칙의 예외입니다. `package.json`의 `name`, 매니페스트 이름, `.mcp.json` 조각의 서버 이름(`tb-slack-agent-org-dash`), 이미지 이름(`ghcr.io/hwahee/slack-agent-org-dash`)이 여기서 나옵니다.
- **제품을 바꾸지 않음**:
  - `slack-agent-org`는 커밋을 고정한 의존성(`package.json`의 `github:hwahee/slack-agent-org#<sha>`)으로 넣습니다. 진단 계약(`src/diag/events.ts`의 `validateRecord`, `validateSnapshot`, 타입, `DIAG_VERSION`)을 **그 파일 그대로** 가져다 씁니다. 계약을 이 레포에 다시 쓰지 않습니다.
  - 의존성 코드는 `node_modules`에만 있고 이 레포에서 고치지 않습니다(패치·`patchedDependencies` 금지).
  - 코어는 제품의 데이터 폴더를 **읽기만** 합니다. ESLint가 `src/server/testbed/cores/agent/`에서 파일 쓰기·삭제·이름 변경 API(`writeFile`, `appendFile`, `rm`, `unlink`, `rename`, `mkdir`, `Bun.write` 등)를 막고, 통합 테스트가 코어가 돈 뒤 데이터 폴더의 파일 목록·크기·수정 시각·내용 해시가 그대로인지 확인합니다.
  - 제품에 아무것도 보내지 않습니다. Slack에 연결하지 않습니다(같은 앱 토큰으로 Socket Mode를 열면 제품의 이벤트를 나눠 가져가 고치려던 증상을 직접 만들기 때문).
- **샘플 코어**: 이 테스트베드에서는 등록하지 않습니다(`CORES`, 대시보드, 포트에서 빠짐). `src/server/testbed/cores/sample/`의 파일(코어와 스모크 시나리오)은 공통 런타임의 시험이 고정 데이터로 import하거나 불러오므로 남깁니다. 이 테스트베드의 `testbed:smoke`에서 샘플 시나리오는 코어가 없어 SKIP입니다. 샘플 코어를 시험 전용으로 옮기는 일은 `testbed-base`에 제안합니다.
- **코어는 in-proc 하나**(`agent`). 파일을 읽는 일이라 외부 프로세스가 필요 없습니다(결정 10에 해당 없음). 복제 없음.
- **포트 블록**: 40010–40019. `+0`(40010)이 대시보드·제어면, 데이터면 포트는 열지 않습니다(`testbed-base`의 `docs/testbed/ports.md` 등록 PR).
- **시간 기준**: 기록의 시각(`t`)은 제품의 벽시계입니다. 이 테스트베드는 같은 맥에서 돌므로 시계 차이를 보정하지 않습니다.
- **Slack ping 간격**: 실측 약 10초(2026-11-25, Bun 1.4.2). 그래서 마지막 ping이 30초 넘게 멈추면 "귀가 먹음"으로 봅니다(7절 `pingStaleSec`).
- **대시보드 배치는 안 C**(실시간 모니터 / 지난 기록, 10.5)이고, `testbed-base`에 P6(프레임·배치 분리)가 들어온 뒤 M3b를 합니다(2026-11-27 사람이 정함). 그때까지 공통 대시보드 UI 시험(`bun run test:ui`)은 샘플 코어가 떠 있다고 가정하므로 이 레포의 CI에서 실패한 채로 둡니다. 시험을 끄거나 건너뛰지 않습니다. P6의 계약 시험(배치 어댑터)으로 바뀌면 풀립니다.
- 결함 주입은 하지 않습니다. 관찰 코어이고 제품의 동작을 바꾸지 않는 것이 목적이기 때문입니다(`faults: []`, 지원 종류 없음).

## 3. 구성

| 코어 id | 유형                | 실행    | 복제 | 하는 일                                                                      |
| ------- | ------------------- | ------- | ---- | ---------------------------------------------------------------------------- |
| `agent` | `passive`(13절 1번) | in-proc | –    | 제품의 진단 기록과 상태 스냅샷을 읽어 이벤트로 옮기고, 수신 건강 상태를 판정 |

- **포트**: `PORT=40010`(대시보드·제어면). 데이터면 없음 → `status().endpoints`는 빈 목록입니다.
- **제품 쪽 위치**: 제품의 `<DATA_DIR>/diag/`(기본 `~/Agent/slack-agent-org/data/diag`). 이 레포를 제품 옆(`~/Agent/slack-agent-org-dash`)에 두면 기본값 `../slack-agent-org/data`가 맞습니다.
- **바인딩**: 로컬 실행 기본 `TESTBED_BIND_HOST=127.0.0.1`(13절 2번).

## 4. 상호작용 프로토콜

제품과의 상호작용은 **파일 읽기**뿐입니다. 형식의 원본은 제품의 `docs/diagnostics.md`(계약 v1)와 `src/diag/events.ts`입니다.

| 파일                                   | 형식                                                                     | 읽는 방법                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `<dataDir>/diag/diag-YYYY-MM-DD.jsonl` | 한 줄에 기록 하나. 공통 필드 `v, t, mono, boot, seq, kind` + kind별 필드 | 파일마다 읽은 바이트 위치를 기억하고 `pollMs`마다 늘어난 부분만 읽음. 마지막 줄이 줄바꿈 없이 끝나면 다음 읽기까지 미룸 |
| `<dataDir>/diag/status.json`           | 상태 스냅샷(제품이 5초마다 원자적으로 교체)                              | `pollMs`마다 통째로 읽음                                                                                                |

- **버전**: 기록의 `v`가 고정한 의존성의 `DIAG_VERSION`과 다르면 그 기록은 해석하지 않고 `agent.contract.mismatch`를 한 번 냅니다(부팅·파일마다 한 번).
- **새 날짜 파일**: 목록을 `pollMs`마다 다시 보고, 처음 보는 파일은 처음부터 읽습니다.
- **파일이 줄어들거나 사라짐**: 크기가 기억한 위치보다 작으면 처음부터 다시 읽습니다. 사라진 파일(제품의 보존 기간 정리)은 잊습니다.
- **파일이 없음**: `diag/` 폴더나 `status.json`이 없으면 건강 상태 `absent`. 오류가 아닙니다(제품이 `DIAG=off`이거나 아직 한 번도 안 떴을 수 있음).
- **잘못된 줄**: JSON이 아니거나 `validateRecord`를 통과하지 못한 줄은 `agent.record.invalid`로 남기고 건너뜁니다.
- **한 번에 읽는 양**: 한 번의 읽기에서 파일당 최대 1MiB. 넘으면 다음 읽기에서 이어 읽습니다.

## 5. 코어 동작 명세

### 5.1 시작과 지난 기록

1. `start`: `<dataDir>/diag/`의 `diag-*.jsonl` 중 지금부터 `backfillMinutes` 안의 날짜 파일을 읽어, 그 구간의 기록을 이벤트로 냅니다(`payload.replayed: true`). 그보다 오래된 기록은 건너뜁니다. 그 뒤 모든 파일의 읽은 위치를 끝으로 맞추고 따라가기를 시작합니다.
2. `backfillMinutes: 0`이면 지난 기록을 내지 않습니다.
3. `stop`: 따라가기를 멈춥니다. `reset`: 읽은 위치·카운터·건강 상태를 비우고, 다음 읽기에서 1번부터 다시 합니다.

### 5.2 기록 → 이벤트

- 기록 하나가 이벤트 하나입니다. 이벤트 kind는 `agent.` + 기록의 `kind`입니다(예: `socket.closed` → `agent.socket.closed`).
- 이벤트의 `ts`는 테스트베드가 읽은 시각이고, 기록의 원래 시각은 `payload.t`에 있습니다. 시간순 판단은 `payload.t`로 합니다.
- payload는 기록 전체(공통 필드 포함) + `file`(파일 이름) + `replayed`(지난 기록이면 `true`)입니다.
- `actor`는 `product`입니다.
- level과 summary는 6절 표를 따릅니다. 표에 없는 kind(제품이 같은 버전에서 kind를 추가한 경우)는 `info`, summary `<kind>`로 냅니다.
- `correlationId`: `message.observed`는 메시지 id(`채널:ts`), `socket.envelope`는 `channel`과 `ts`가 있으면 `채널:ts`. 그래서 한 메시지의 envelope와 관찰 기록이 상세 패널에서 묶입니다.
- `latencyMs`: `message.observed`는 `delayMs`, `turn.ended`는 `ms`, `inbox.taken`은 그 묶음의 가장 긴 `waitedMs`.

### 5.3 수신 건강 상태

`pollMs`마다 `status.json`과 지금 시각으로 판정합니다. 위에서부터 처음 맞는 것이 상태입니다.

| 상태           | 조건                                                                            | 뜻                                                              |
| -------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `absent`       | `status.json`이 없거나 읽을 수 없음, 또는 `validateSnapshot`을 통과하지 못함    | 진단이 꺼졌거나 제품이 없음                                     |
| `stopped`      | `writtenAt`이 `snapshotStaleSec`보다 오래됨                                     | 제품 프로세스가 멈췄거나 꺼짐                                   |
| `disconnected` | `sections.socket`이 없거나 `live: false`                                        | 연결 끊김(제품이 알고 있음, 재연결 중)                          |
| `deaf`         | `live: true`인데 `lastPingAt`(없으면 `connectedAt`)이 `pingStaleSec`보다 오래됨 | **반쯤 죽은 소켓**: 제품은 연결됐다고 믿지만 아무것도 오지 않음 |
| `ok`           | 그 밖                                                                           | 정상                                                            |

- 나이(age)는 테스트베드의 지금 시각 − 스냅샷의 시각입니다.
- **잠자기 보정**: 테스트베드 자신의 폴링 간격이 `pollMs + 5000`ms보다 길었으면(이 맥도 잠들었다 깸) 그 회차는 판정하지 않고 다음 회차로 미룹니다. 깨어난 직후 제품이 스냅샷을 쓰기 전에 `stopped`로 튀지 않게 하기 위함입니다.
- 상태가 바뀔 때만 `agent.health.changed`를 냅니다(시작 후 첫 판정도 `from: null`로 냄).

### 5.4 경계와 실패

| 상황                                                     | 동작                                                                                          |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `dataDir`가 없음                                         | 시작은 성공, 건강 `absent`. 폴더가 생기면 그때부터 읽음                                       |
| `dataDir`가 파일이거나 읽기 권한 없음                    | 시작은 성공, 건강 `absent`, `agent.source.unreadable`(warn)을 원인과 함께 한 번 냄            |
| 한 줄이 1MiB보다 김                                      | 그 줄을 `agent.record.invalid`(`problem: 'line too long'`)로 남기고 다음 줄바꿈부터 이어 읽음 |
| 기록 하나의 payload가 `TESTBED_MAX_PAYLOAD_BYTES`를 넘음 | 공통 런타임의 자르기를 따름(`truncated: true`)                                                |
| 같은 줄을 두 번 읽음(파일이 다시 써짐)                   | 기록의 `boot`+`seq`가 이번 부팅에서 이미 낸 것이면 다시 내지 않음                             |
| 제품이 재부팅함(`boot` 바뀜)                             | 그대로 따라감. `agent.process.booted`가 경계를 알림                                           |

| `agent.turn.ended`                  | `ok: false`면 warn, 그 밖 info                                                                                    | `턴 끝 {conversation} {ms/1000}s {ok ? '' : '실패'}`                                               |
| `agent.triage.decided`              | `failed`·`unreadable`이면 warn, 그 밖 info                                                                        | `채널 판단 {conversation}: {outcome}`                                                              |
| `agent.poll.ran`                    | 작업 중 `ok: false`가 있으면 warn, 그 밖 debug                                                                    | `폴링 {ms}ms {skipped ? '(건너뜀)' : ''}`                                                          |
| `agent.catchup.ran`                 | `error`가 있으면 warn, `found > 0`이면 info, 그 밖 debug                                                          | `따라잡기 ({trigger}) {found}건 찾음` / `따라잡기 ({trigger}) 실패: {error}`                       |
| `agent.heartbeat.beat`              | `working`이면 debug, 그 밖 warn                                                                                   | `하트비트 {outcome}{problem ? ': ' + problem : ''}`                                                |

- 숫자는 summary에서 초 단위로 줄일 때 소수 한 자리까지 씁니다. 지난 기록(`replayed`)이면 summary 앞에 `[지난 기록] `을 붙입니다.
- 기본 `eventLevel: 'info'`이므로 debug 이벤트(하트비트·폴링·평범한 envelope)는 링버퍼에 남지 않습니다. 원본은 언제나 제품의 파일에 있습니다.

### 6.2 이 테스트베드가 만드는 이벤트

| kind                      | level                                                           | 언제                                 | summary 형식                                                      | payload                                                                      |
| ------------------------- | --------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `agent.health.changed`    | `ok` info, `disconnected`·`absent` warn, `deaf`·`stopped` error | 건강 상태가 바뀔 때(5.3)             | `수신 상태 {from ?? '처음'} → {to}: {reason}`                     | `{ from, to, reason, snapshotAgeMs, pingAgeMs, conn, boot }` (모르면 `null`) |
| `agent.record.invalid`    | warn                                                            | 해석할 수 없는 줄(4절, 5.4)          | `읽을 수 없는 기록 {file}:{line} — {problem}`                     | `{ file, line, problem, preview }` (`preview`는 앞 200자)                    |
| `agent.contract.mismatch` | error                                                           | 기록의 `v`가 고정한 계약 버전과 다름 | `진단 계약 버전이 다름: 파일 v{found}, 이 테스트베드 v{expected}` | `{ file, found, expected }`                                                  |
| `agent.source.unreadable` | warn                                                            | `dataDir`를 읽을 수 없음(5.4)        | `진단 폴더를 읽을 수 없음: {error}`                               | `{ dataDir, error }`                                                         |

`reason` 문장 예: `마지막 ping 31.2s 전`, `스냅샷 42.0s 전`, `status.json 없음`, `소켓 live=false`, `정상 (ping 3.1s 전)`.

## 9. 제어 표면

| 액션           | 입력                                                                                        | 출력                                                                                                                                                                                                                                                                                                                                       | 부작용 | 락  | REST/MCP/UI |
| -------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------ | --- | ----------- |
| `snapshot`     | `{}`                                                                                        | `{ health, reason, judgedAt, snapshotAgeMs, pingAgeMs, frameAgeMs, files: string[], status: <status.json 그대로> \| null }`                                                                                                                                                                                                                | 없음   | –   | 셋 다       |
| `scan_history` | `{ hours?: 1–168 (기본 24), since?: ISO, until?: ISO }` — `since`가 있으면 `hours`보다 우선 | `{ from, to, records, invalid, byKind: Record<kind, n>, boots: string[], socket: { connections, closes: { t, conn, code, livedMs }[], disconnectRequests, reconnectFailures }, messages: { socket, catchup, rescued: { t, id, delayMs, outcome }[] (최대 50, 늦은 순) }, clockGaps: { count, totalMs, maxMs }, turns: { count, failed } }` | 없음   | –   | 셋 다       |

- 두 액션 모두 파일을 읽기만 하고 이벤트 버스에 아무것도 내지 않습니다. MCP 도구 이름은 `agent_snapshot`, `agent_scan_history`입니다.
- `scan_history`는 기간 안의 날짜 파일만 엽니다. 기간이 7일을 넘거나 `since`가 `until`보다 늦으면 `VALIDATION_ERROR`입니다.
- `rescued`는 `path: catchup`이고 `outcome`이 `queued` 또는 `overheard`인 메시지입니다(사람이 보낸 말을 귀가 놓친 경우).
- 공통 도구로 충분한 것: 이력 판정은 `check`로 합니다. 예: 귀가 놓친 메시지가 없었는가 = `check({ kind: 'agent.message.observed', level: 'warn' }, { none: true })`, 반쯤 죽은 소켓이 없었는가 = `check({ kind: 'agent.health.changed', text: '→ deaf' }, { none: true })`.

### 10.3 데이터와 표현

| 데이터                                                               | 성격                   | 표현                                                     | 이유                                                                                   |
| -------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 수신 건강 상태(`ok`·`deaf`·`disconnected`·`stopped`·`absent`)와 이유 | 상태                   | 크게 쓴 한 단어 + 이유 한 줄, 상태별 색(토큰)            | 장면 "답이 늦을 때"의 첫 질문. 읽는 데 1초를 넘기면 안 됨                              |
| 마지막 ping 나이, 스냅샷 나이                                        | 시계열(초 단위로 변함) | 1초마다 오르는 숫자 + 문턱(`pingStaleSec`) 표시          | 30초 문턱에 얼마나 가까운지가 판단의 근거                                              |
| 그 상태가 된 시각(마지막 `agent.health.changed`)                     | 상태                   | "deaf since 11-26 09:09 (31.7시간)" 한 줄                | "언제부터 먹통인가"                                                                    |
| 연결의 일생(`socket.hello`·`closed`·`reconnect-*`)                   | 흐름(구간)             | 시간축의 가로 막대(연결 번호별), 끊긴 자리는 표시        | 끊김을 제품이 알아챘는지(막대가 끝남) 몰랐는지(막대는 이어지는데 ping이 멈춤)를 한눈에 |
| 잠자기(`clock.gap`)                                                  | 흐름(구간)             | 시간축의 음영 구간                                       | 끊김·먹통의 원인 후보를 같은 축에서                                                    |
| 건강 상태의 변화                                                     | 흐름(구간)             | 시간축 맨 위의 상태 띠(색)                               | 연결 막대·잠자기와 겹쳐 봐야 원인이 보임                                               |
| 메시지(`message.observed`: 경로·지연·결과)                           | 흐름(점) + 대기열      | 시간축의 점(소켓/따라잡기 색), 최근 목록(경로·지연·결과) | "내 메시지는 들어왔나, 어느 길로, 얼마나 늦게"                                         |
| 귀가 놓친 메시지(`rescued`)                                          | 판정                   | 늦은 순 목록, 개수 배지                                  | 아침 장면의 핵심 수. 0이면 "없음"이라고 씀                                             |
| 따라잡기 실행(`catchup.ran`: trigger·found)                          | 흐름(점)               | 시간축의 눈금                                            | 놓친 메시지를 건진 것이 폴링인지 재연결인지                                            |
| 대기열 길이, 지금 턴(`status.json`의 inbox·turn)                     | 상태                   | 작은 숫자 두 개                                          | 메시지가 들어왔는데 처리가 늦는 경우를 구분                                            |
| 기간 합계(`scan_history`)                                            | 비교                   | 요약 카드(끊김·놓친 메시지·잠자기·턴) + 기간 선택        | 며칠 만에 열었을 때 이벤트를 다 훑지 않고 답을 얻음                                    |
| 원래 이벤트(`agent.*`), Run, 에이전트 타임라인                       | 흐름                   | 공통 위젯 그대로                                         | 세부 확인과 재현 실험용. 새로 만들 이유 없음                                           |

- 시간축의 기본 폭은 최근 6시간이고, 1시간·24시간·7일로 바꿉니다. 7일은 `scan_history`와 지난 기록(`backfillMinutes`)이 허락하는 범위 안에서 그립니다.
- 시간은 화면에서 현지 시각(KST)으로 보여 주고, 툴팁에 UTC를 같이 둡니다.

## 11. 마일스톤과 수용 기준

### M1 — 관찰 코어, 이벤트, 설정, 샘플 코어 빼기

- 레포 준비: `package.json` `name`, 워크플로 `IMAGE`, 포트 40010(`Dockerfile`, `.env.example`, 워크플로 이미지 job의 `-p 40010-40019:40010-40019`, 서버 `PORT` 기본값). 빠진 곳이 없는지 `4000`으로 검색한 결과를 PR에 적습니다.
- `slack-agent-org` 의존성(커밋 고정), `agent` 코어(4–7절), 샘플 코어 등록 해제(2절), 읽기 전용 ESLint 규칙.
- 수용 기준
  1. `bun run check` 통과.
  2. 통합 테스트(임시 폴더에 제품의 기록·스냅샷을 써 가며):
     - 기록 한 줄을 덧붙이면 `pollMs` + 500ms 안에 해당 `agent.*` 이벤트가 나오고, level·summary·correlationId·latencyMs가 6절과 같음(kind마다 하나 이상).
     - 줄바꿈 없이 끝난 줄은 줄바꿈이 붙은 뒤에야 이벤트가 됨.
     - 새 날짜 파일, 줄어든 파일, 사라진 파일, 1MiB 넘는 줄, JSON이 아닌 줄, `v: 2`인 줄(4절, 5.4).
     - 건강 상태: 스냅샷을 바꿔 `absent` → `ok` → `deaf` → `disconnected` → `ok` → `stopped`를 차례로 만들면 `agent.health.changed`가 그 순서로 정확히 한 번씩 나옴. 테스트베드 자신의 폴링이 늦은 회차는 판정하지 않음.
     - `backfillMinutes` 안의 기록만 `replayed: true`로 나옴, `0`이면 하나도 안 나옴.
     - **읽기 전용**: 코어를 시작·리셋·정지하는 동안 데이터 폴더의 파일 목록·크기·mtime·sha256이 바뀌지 않음.
  3. `bun run lint`가 `cores/agent/`의 `writeFile` 등 쓰기 API 사용을 오류로 잡음(린트 규칙 시험).
  4. 매니페스트에 `sample`이 없고 `agent`만 있음, `agent`의 `endpoints`는 빈 목록.

### M2 — 액션, 제어면, 스모크

- `snapshot`, `scan_history`(9절)와 스모크 시나리오. 스모크는 레포에 넣은 **합성 고정 데이터**(`fixtures/agent-data/`, 실제 제품 데이터 아님)를 `set_config`의 `dataDir`로 가리켜 쓰고, 끝나면 원래 `dataDir`로 되돌립니다. 고정 데이터는 고정한 계약을 통과해야 합니다(단위 테스트).
- 수용 기준(`bun run testbed:smoke` 통과, 액션 커버리지 포함)
  1. `testbed_info` → 코어 `agent`가 running, 데이터면 주소 없음.
  2. `set_config({ core: 'agent', patch: { dataDir: 'fixtures/agent-data' } })` → `result: 'restart-required'` → `stop` → `start` → `agent_snapshot` 결과의 `health`가 `stopped`(고정 데이터라 스냅샷이 오래됨), `files`가 `['diag-2026-01-02.jsonl']`.
  3. `agent_scan_history({ since: <고정 데이터 시작>, until: <끝> })` → `messages.rescued`에 고정 데이터의 놓친 DM 1건(지연 ≥ 60000ms), `socket.closes` 1건, `clockGaps.count` ≥ 1.
  4. `agent_scan_history({ hours: 200 })`와 8일짜리 `since`·`until` → `VALIDATION_ERROR`.
  5. `set_config({ core: 'agent', patch: { faults: [{ id: 'x', delayMs: 10 }] } })` → `VALIDATION_ERROR`.

### M3a — 대시보드 설계

- 10.3–10.4를 쓰고 구조가 다른 배치안 2–3개를 낸 뒤 멈춥니다. 사람이 고르면 10.5·10.6과 2절을 고칩니다.

### M3b — 배치와 고유 화면

- `testbed-base` P6를 머지한 뒤(업그레이드 가이드를 따름) 10.5의 안 C를 만듭니다. 수용 기준: `bun run test:ui`(P6의 계약 시험 + 10.2 핵심 질문마다 장면 시험), 캡처와 별도 에이전트의 검토를 PR에 첨부. 장면 시험 예: 1440px에서 `/`를 열면 스크롤 없이 수신 상태(`deaf`면 그 단어와 마지막 ping 나이)가 보임.

### M4 — 이미지, 워크플로, `docs/agent-usage.md`

- 이미지는 제품의 데이터 폴더를 **읽기 전용 마운트**로 받습니다(`-v ~/Agent/slack-agent-org/data:/data:ro -e AGENT_DATA_DIR=/data`).
- 수용 기준: 이미지를 띄운 뒤 `bun run testbed:smoke --url http://127.0.0.1:40010` 통과, `docs/agent-usage.md`에 `.mcp.json` 조각·CLAUDE.md 스니펫·맥에서 띄우는 방법이 있음.

## 12. 범위 밖

- 자동 복구(재연결 지시, 제품 재시작). 이 테스트베드는 제품에 아무것도 하지 않습니다.
- Slack 연결, Slack API 호출, 테스트 메시지 발신.
- 제품의 사람용 로그(`agent.log`) 해석. 문구가 계약이 아니기 때문입니다.
- OS 수준 관찰(`nettop`, `pmset`, `lsof`). 제품의 진단 기록이 ping과 시계 공백을 이미 담고 있어 지금은 필요 없습니다.
- 여러 에이전트(두 번째 장비) 동시 관찰. 생기면 코어 설정을 여러 개로 늘리는 변경으로 다룹니다.

## 13. 사람에게 확인할 결정

1. **코어 유형** — 공통 런타임의 유형(passive·active·scenario)에 "파일을 읽는 관찰자"가 따로 없습니다. 방향(제품 → 코어)과 자동 시작이 맞는 `passive`로 두었습니다(데이터면 없음). 그대로 갈지, `testbed-base`에 관찰자 유형을 제안할지. M1–M2는 이 값과 상관없이 진행합니다.
2. **대시보드를 보는 곳** — 에이전트 맥에서만(`127.0.0.1:40010`)으로 두었습니다. 다른 기기(Tailscale 등)에서도 보려면 바인딩과 접근 제어를 정해야 합니다. M4에 영향.
3. **맥에서 상시 실행** — 수동 `bun run start`, launchd 서비스, Docker 중 무엇으로 띄워 둘지. M4에 영향.
