# 스펙 템플릿

각 테스트베드 레포의 `docs/spec.md`가 따르는 틀입니다. 스펙은 그 테스트베드의 구현 세부사항 원본입니다.

## 1. 틀

<!-- 검증 대상 제품·기능. 이 테스트베드 없이 무엇이 어려운가 -->

## 2. 확정된 전제

<!-- 재검토·대안 제시 금지 항목. 13절에서 정해진 결정도 여기로 옮김 -->

## 2. 마일스톤

스펙마다 기본 4개이고, 각각 따로 검증할 수 있어야 합니다. 마일스톤 하나는 PR 하나입니다.

| M   | 범위                                                             | 완료 판정                              |
| --- | ---------------------------------------------------------------- | -------------------------------------- |
| M1  | 코어 + 이벤트 + 설정 + 결함                                      | 코어 단위·통합 테스트, `bun run check` |
| M2  | 액션, 제어면 노출(REST/MCP), 매니페스트                          | MCP 스모크 통과                        |
| M3  | 대시보드 고유 패널                                               | testid 기반 UI 자동화(핵심 흐름)       |
| M4  | Docker 이미지, GitHub Actions 이미지 push, `docs/agent-usage.md` | 이미지 기동 후 스모크, 문서 존재       |

## 3. 좋은 스펙의 기준

1. **계약은 엄격하게, 구조는 맡기기.** 이벤트, 설정, 액션, 프로토콜, 수용 기준은 빠짐없이 정합니다. 파일 경로와 내부 구조는 공통 런타임 규약을 따르게 하고 따로 지정하지 않습니다.
2. **공통 런타임을 다시 쓰지 않기.** 락, Run, 봉투, REST/MCP 공통 도구는 `docs/testbed/*`를 참조만 합니다. 스펙에는 이 테스트베드만의 것만 씁니다.
3. **모호함을 남기지 않기.** 모든 항목은 "확정"(2절) 아니면 "사람에게 확인"(13절)입니다. "적절히", "필요하면" 같은 표현을 쓰지 않습니다.
4. **수용 기준은 실행 가능하게.** 예: "`start_run` → 제품이 `/v1/chat/completions`를 stream=true로 호출 → `check(kind='llm.completion.responded', count=='1')` pass → `get_event` payload의 `chunks` ≥ 2"
5. **경계와 실패를 먼저.** 정상 경로보다 시간 초과, 큰 입력, 잘못된 형식, 끊김 동작을 더 자세히 씁니다. 테스트베드는 제품의 실패 처리를 보는 도구이기 때문입니다.
6. **표 우선.** 이벤트, 설정, 액션, 결함은 표로 씁니다.
7. **분량.** 마일스톤 하나가 PR 하나에 들어갈 크기로 나눕니다.

## 4. 스펙을 쓰기 전에 확인할 것

- 검증 대상 제품과 기능, 시험 장면(사람이 쓸 때 / 에이전트가 쓸 때)
- 유형(passive / active / scenario), 코어 개수, 외부 프로세스 여부와 이유, 복제
- 프로토콜과 버전, 데이터면 포트 수, 상태(세션, 스트림)
- 제품의 어떤 실패 처리를 보고 싶은가 → 결함 종류
- 공통 도구로 안 되는 고유 동작 → 액션
- 사람이 대시보드에서 꼭 눈으로 봐야 하는 것 → 고유 패널
- 배포 형태(로컬 / 공용 / 클라우드 다중), 인증
- 수용 시나리오 3–5개

## 5. 스펙이 바뀔 때

- 같은 `docs/spec.md`를 고칩니다. 변경 이력 맨 위에 날짜, 바뀐 절, 영향받는 마일스톤을 적고, 바뀐 수용 기준을 함께 고칩니다.
- 구현하는 에이전트는 "변경 이력의 최신 항목을 반영"하라는 지시를 받으면 그 항목의 절과 수용 기준만 보고 작업합니다.
